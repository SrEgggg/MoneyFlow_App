# MoneyFlow QA and UI/UX review — 27 September 2026

> Historical findings. See [the fixes](QA_FIXES_2026-09-27.md) and [current release checklist](../../RELEASE_SETUP.md) for their status.

Implementation follow-up: [QA fixes and verification](QA_FIXES_2026-09-27.md). The findings below are the original pre-fix audit.

## Verdict and scope

The main UI is cohesive, and the normal financial flows have useful regression coverage. I would not release this build yet: reproducible failures remain in account identity, money precision, backup validation, and the handling of errors after a successful database write.

Review only. No application source, financial records, or saved preferences were changed. The additional QA harness and logs are under `build/`; the tests use isolated in-memory databases. This report is the only new project document.

Executed in this review:

- `flutter analyze`: no issues.
- `flutter test --reporter expanded`: all 111 existing tests passed, including the 80-combination screen/theme/text-size matrix. Configurations are 320×640, 390×844, 430×932 at normal scale, 320×640 at 1.6×, and 390×844 at 2×, across eight screens and two themes.
- `flutter test build/qa_audit_test.dart --reporter expanded`: 11 characterization probes reproduced the behaviors described below. These tests deliberately assert the current faulty behavior; their passing does NOT mean the defects are fixed.
- Inspected freshly generated Home/dark and Performance/light renders, and reviewed forms, routes, repositories, settings, backup, startup, Android manifest/signing and theme/layout test coverage.
- `flutter devices` and `flutter emulators`: Windows and browsers are available; no connected Android device or installed emulator. The app was exercised through Flutter's widget-test runtime, not a native Android session. No new APK build was run for this review.

Existing passing coverage includes transfer atomicity/overspending/concurrency, transaction add/edit/delete and Undo, goal recommendations/date edge cases, custom categories, navigation, theme persistence, database close/reopen, backup round trips, recurring scheduling, and keyboard/layout scenarios. These are automated checks, not a claim that every UI control was manually tested.

Not tested: native photo picker and process-death recovery, TalkBack, actual Android keyboard variants, installation/upgrade on a phone, airplane mode on a phone, background lifecycle, release-mode frame timings, low-memory behavior, or OS backup/restore. No network client/telemetry code was found in the inspected `lib` source or direct dependencies; this is not a network traffic or dependency-security audit.

## Findings

**Reproduced** means an executed isolated probe. **Code-confirmed** means the implementation establishes the issue, without claiming a physical-device reproduction. **Potential** requires fault injection, native testing, or profiling beyond the evidence stated. **Optional** is product simplification, not a defect. High means block release; Medium means fix soon; Low means polish.

| Screen/feature | Issue | Steps to reproduce | Expected vs. actual behavior | Severity | Recommended fix |
|---|---|---|---|---|---|
| Accounts / Move money | **Reproduced:** duplicate account names are accepted and break money entry. | Create two accounts named Cash. Open Move money or record an expense from Cash. Tested repository insertion and duplicate-name dialog rendering. | Names should identify one account. Both rows are saved; the move dialog asserts in debug; expense recording rolls back because two accounts match. Release UI behavior was not tested. | High | Validate normalized names on create/edit and enforce uniqueness at storage level. Prefer immutable account IDs for references. Migrate existing duplicates deliberately without dropping records. |
| Backup restore: completeness | **Reproduced:** an incomplete current-format backup silently deletes omitted data. | Export, remove `journal_entries` from the JSON's tables, then restore. | Reject an incomplete current-format file before replacement. Restore succeeds and wipes the existing journal. Other optional unchecked tables have the same code path. | High | Validate the complete format-specific table manifest before any replacement; allow absent tables only for explicitly supported older formats. |
| Backup restore: row validity | **Reproduced:** invalid financial/date values bypass repository validation. | Change a backed-up transaction amount to -500 and its date to `not-a-date`; restore. | Reject invalid rows and leave current data intact. Restore commits the values; reading transactions throws FormatException. Startup recalculation also reads those rows, so startup is at risk (not launched against this corrupted fixture). | High | Validate every row's types, money precision/ranges, dates, enums, IDs, account references and cross-record consistency before committing. Reject duplicate IDs instead of silently replacing them. |
| Transactions / persistence | **Reproduced under injected failure:** a save can commit, throw, and duplicate on retry. | Inject recalculation failure after insert, call Save, then retry. | One committed entry with an explicit saved state. Both calls throw while two entries persist and Cash falls from 1,000 to 980. Quick Add says to check History, but History can still be stale because refresh follows recalculation. | High | Separate the durable write result from cache/refresh errors. Return the saved ID immediately, refresh authoritative state, retry derived calculations separately, and make retries idempotent. Do not hold a committed form in an unsaved state. |
| Goals | **Reproduced:** decimal accumulation prevents exact completion/withdrawal. | Set target ₱0.80; add ₱0.10 then ₱0.70; try removing ₱0.80. | Completed goal and exact withdrawal. Stored value is slightly below 0.80, status stays active, and the withdrawal is rejected. The same floating-point class applies to other amounts. | High | Use integer centavos or consistently quantize every goal write/comparison. Migrate existing amounts carefully and reconcile status with rounded totals. |
| Accounts: balance validation | **Reproduced:** oversized balances swallow valid money movements. | Enter 1000000000000000000 as account balance, then deposit ₱10. The UI/repository allow finite values without a maximum. | Reject unsupported values. The income row records ₱10 while the account balance is unchanged due to numeric precision. | High | Use one bounded centavo policy for accounts, goals, transactions and imports, including two-decimal validation. Avoid unrestricted direct balance edits; explain and record intentional balance adjustments. |
| Goals: repository validation | **Reproduced at repository level:** sub-cent targets create impossible goals. | Insert/import target 0.001; attempt contributions of 0.001 and 0.01. | Reject the target. It saves, but one contribution fails precision validation and the other exceeds the target. Normal goal typing has a two-decimal formatter; this is a repository/import gap. | Medium | Apply identical money validation in the repository and restore layer, not only keyboard formatters. |
| Settings / financial-day calculations | **Reproduced:** changing cutoff leaves cached daily totals in the old day. | Record a 02:00 transaction, recompute with cutoff 03:00, change cutoff to 00:00. | Cached analytics should refresh. The row stays assigned to the previous day until another recalculation. Separately, Calendar/Overview intentionally use calendar dates while Advanced Analytics uses cutoff-based cache. | Medium | Recompute/invalidate derived data on cutoff change; clearly define and label which screens use financial days versus calendar dates. |
| Transaction editing | **Reproduced model behavior; code-confirmed form path:** erased notes/tags are retained. | Edit an entry with notes/tags, erase them and save. | Blank fields clear the values. The form passes null, but copyWith treats null as “keep old value.” | Medium | Add explicit nullable-field clearing semantics. Verify clearing through the UI, database reopen and backup. |
| Transaction search / account filter | **Reproduced search; code-confirmed filter:** receiving accounts are omitted. | Record Cash → GCash, with no source transaction from GCash; search GCash or open account filter. | Find that transfer and offer GCash. Search checks only source account; filter choices are also built only from sources. | Medium | Include source and destination names in search/filter option construction. Keep transfer type/amount semantics unchanged. |
| Journal / Monthly Reviews | **Code-confirmed:** existing screens have no reachable navigation entry. | Inspect Performance's two tabs and available actions. Search references to JournalTab, ReviewsTab and performanceMonth. | Existing records/features remain accessible. JournalTab and ReviewsTab are never mounted; the monthly-review route's only link is in the unmounted ReviewsTab. Stored data remains present. | High (feature regression) | Restore compact secondary entry points without adding more top-level tabs. Preserve existing journal/review data. |
| Settings: export / restore | **Code-confirmed workflow gap:** no external save/share or file picker. | Export, then try choosing a file for a fresh-install restore. | Save a portable file and choose/preview the intended backup. Export copies a documents-directory path; restore automatically selects the newest local file by modification time. No external file selection exists. Native file-manager access was not tested. | High for a release promising backup | Use native save/share and open-document flows; preview filename/date/counts before destructive confirmation. Keep snapshots internally consistent. Disable export/restore controls while processing. |
| Android release signing | **Code-confirmed:** release build uses debug signing configuration. | Inspect android/app/build.gradle.kts release block. | A release signing setup. It uses signingConfigs.getByName("debug"). | High / release blocker | Configure an upload/release key outside source control and verify the signed release bundle. No key was generated or changed during this review. |
| Privacy: “No cloud” claim | **Potential OS-backup inconsistency:** manifest does not declare an explicit backup/data-extraction policy. | Inspect the manifest and About copy; verify OS backup on a supported phone. | Product wording matches platform behavior. About promises all data remains on this device, while Android's default backup behavior can include app files. Actual cloud transfer was not tested. | Medium; resolve before privacy publication | Choose and test an explicit OS backup policy, including finance database and photo-bearing snapshots, and make the copy accurate. See Android's official Auto Backup documentation below. |
| Clear all data / local snapshots | **Code-confirmed:** clearing the database leaves exported backups. | Export, then Clear all data. Inspect BackupService.exportToFile versus AppDatabase.wipe. | Explain whether saved snapshots remain, or remove internal snapshots as part of an explicit clear operation. wipe deletes SQLite rows only; the old JSON still contains financial data, notes and photos and remains eligible for restore. | Medium / privacy | State the retention policy in the confirmation; include internal snapshot cleanup when “all app data” is intended. Do not silently delete user-managed external backups. |
| Accounts: delete confirmation | **Code-confirmed:** confirmation contradicts repository rules. | Delete an account referenced by a transaction. | Explain that linked records prevent deletion. Dialog says the records will retain the account name; repository instead refuses the deletion. | Medium | Check dependencies before showing the destructive action and explain the actual restriction. Do not encourage deleting financial history merely to hide an account. |
| Accessibility / account colors | **Code-confirmed:** 32dp swatches lack names/selected semantics. | Open Add/Edit account; inspect swatches, then validate with TalkBack on a phone. | Approximately 48dp targets with color name and selected state. GestureDetector wraps a 32×32 colored container with no such semantic information. | Medium | Increase the hit area, add semantic names and selected state, and use a visible check rather than a white border alone. |
| Transaction revisions | **Code-confirmed integrity gap:** audit write is separate from the edit transaction; backup omits revisions. | An edit writes a revision and then fails updating the record; or export/restore into a fresh database. | Revisions describe successful edits and follow a defined backup policy. A failed edit can leave a revision, while exported backups omit this table and replacement restores retain old local revision rows. | Medium | Write revision and edit atomically; explicitly include or clear/reconcile revisions during restore. |
| Performance / loading | **Potential scale issue:** every transaction triggers a full historical recomputation. | Profile many years of records in release mode, then save and scroll same-day-heavy history. | Save latency scales predictably. Code rereads all transactions, clears/rebuilds cache and awaits it before success. History lazily builds days but eagerly builds all rows inside each day. No phone frame timings were measured. | Medium | Benchmark first; incrementally refresh affected days, batch cache writes and flatten long history into lazy rows if measurements justify it. Avoid calling this a measured lag bug yet. |
| Settings / visual hierarchy | **Optional:** small 10–11sp explanatory paragraphs and a developer-oriented demo reset clutter settings. | Open Preferences, Planning, Backup and Data. | Short readable labels and supporting details on demand. Several long explanations use tiny fixed sizes; Reset to demo data is exposed beside real data management. | Low; hide demo reset before release | Shorten descriptions, use shared readable text styles, put backup detail behind Help, and restrict demo reset to debug/demo builds. |
| Performance navigation | **Optional:** Overview and Calendar repeat the same secondary destinations. | Scroll both tabs to Streaks, Achievements and Advanced Analytics. | One predictable place for secondary tools. Both tabs repeat the same three controls; Advanced Analytics overlaps overview content. | Low | Consolidate secondary actions into one menu; retain only analyses that answer a distinct question. Do not remove stored information. |

## What is already working well

- Neutral surfaces, green primary actions and the five-tab structure give the app a recognizable savings-focused identity. No wholesale redesign is warranted.
- Goals show actual savings, remaining amount, progress and expandable guidance. Optional imagery is secondary to the money information.
- Sparse-data analytics show explanations instead of decorative graphs. Transfers are excluded from income/expense aggregates in tested flows and have clear source/destination language.
- Standard transfer operations are atomic, confirmations are present, and tested invalid/concurrent transfers roll back appropriately.
- Primary forms use busy guards; Quick Add has lightweight success feedback and Undo. Existing core theme/contrast and phone/text-size checks pass.
- Close/reopen and valid legacy/current backup tests pass. These successes do not cover the invalid-backup defects found by this audit.

## Prioritized action list

### Must fix before release

1. Reject/resolve duplicate account identities without losing legacy transactions.
2. Make financial writes and user-visible save results reliable; prevent duplicate retries after commit.
3. Unify money precision/bounds, especially goal completion and account balance entry.
4. Validate backup completeness/content before replacement; provide real portable export and intentional file selection.
5. Restore access to Journal and Monthly Reviews, and correct cutoff-cache invalidation.
6. Configure release signing; resolve OS-backup/privacy wording and internal-snapshot retention. Hide demo reset in the production build.
7. Run physical Android acceptance tests: upgrade existing data, restart after edits/transfers, native gallery cancel/recovery, TalkBack, keyboard handling, export/reinstall/import, and offline startup. Measure release-mode save/scroll performance on a lower-end phone.

### Improve next

- Fix notes/tags clearing and destination-account search/filtering.
- Correct account deletion copy, audit revision atomicity and backup policy.
- Increase/label small touch targets; verify accessibility beyond the shared-color contrast tests.
- Add safe busy/error handling around backup and preference writes; distinguish saved data from failed derived refreshes.
- Profile long histories before optimizing cache/list behavior.

### Simplify or remove

- Remove production access to Reset to demo data; keep it in developer tooling.
- Consolidate repeated Performance secondary actions.
- Replace lengthy Settings paragraphs with short labels and optional help.
- Preserve the existing green/charcoal identity, real-data charts and useful whitespace. More decoration is not needed.
